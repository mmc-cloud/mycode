# Database Recovery

数据库恢复任务的首要目标不是尽快修改文件，而是在不破坏原始恢复证据的前提下，尽可能恢复正确、可验证的数据。

## 核心原则

1. **先保护证据，再进行恢复。**

   在执行任何可能打开、回放、checkpoint、rollback、truncate、repair、migrate、rewrite 或删除数据库相关文件的操作前，先识别并保护原始数据及相关事务日志、journal、WAL 或其他 sidecar 文件。

2. **不要在原始输入上直接恢复。**

   将以下对象明确区分：

   - Original evidence：用户提供的原始数据库及相关文件。
   - Working copy：用于调查和恢复的副本。
   - Recovered output：最终恢复出的新数据库或导出结果。

   恢复、修复和验证操作应优先针对 working copy，最终结果写入新的 output，不覆盖 original evidence。

3. **先识别数据库类型和恢复目标。**

   明确：

   - 使用的数据库引擎；
   - 用户希望恢复什么；
   - 当前有哪些数据库文件、日志或 sidecar；
   - 是事务恢复、结构损坏、文件截断、数据丢失还是其他故障。

4. **数据库专用操作前加载对应参考。**

   不同数据库的日志、恢复和一致性机制不同。存在对应 reference 时，在执行数据库专用恢复操作前先读取它。

   对 SQLite 恢复任务，在使用 SQLite 打开、检查或修改数据库前，先读取：

   `references/sqlite.md`

5. **优先采用最少破坏的恢复路径。**

   先判断数据库自身正常的 crash recovery / log replay 是否足够；只有正常机制无法得到正确结果时，再考虑 salvage、page recovery、日志分析或其他更激进的方法。

6. **不要根据缺失证据猜造数据。**

   如果日志缺失、文件损坏或恢复结果存在不确定性，应明确说明能够确认的内容、无法确认的内容以及恢复结果的可信范围。

## 通用工作流

### 1. 调查现场

先使用不会修改数据库状态的方法了解：

- 主数据库文件；
- journal / WAL / transaction log；
- 其他相关 sidecar；
- 文件大小、时间和命名关系；
- 用户要求恢复的具体数据。

此阶段避免直接使用可能触发数据库自动恢复或写入的数据库连接。

### 2. 冻结原始证据

在 workspace 内保存完整 evidence set。

如果同一数据库存在多个相关文件，应作为一组保存，而不是只复制主数据库文件。

条件允许时记录：

- 文件名；
- 大小；
- hash；
- 原始文件与副本的对应关系。

完成后不再对 original evidence 执行恢复性操作。

### 3. 创建工作副本

从保存的 evidence set 创建 working copy。

后续数据库打开、自动恢复、检查、修复和实验操作均针对 working copy。

如果一次实验会改变 working copy，并且后续可能需要尝试其他恢复路径，应重新从 preserved evidence 创建新的 working copy，而不是继续复用已经发生变化的副本。

### 4. 执行数据库专用恢复

根据数据库类型读取对应 reference，然后选择恢复方法。

通常按以下顺序考虑：

1. 数据库自身正常 crash recovery / log replay；
2. 正常读取并导出到新的干净数据库；
3. 官方 recovery / salvage 能力；
4. 更低层的数据页或日志分析。

不要直接跳到最激进的方法。

### 5. 生成独立恢复结果

恢复成功后，将结果写到新的数据库或导出文件。

不要把“working copy 当前能够打开”等同于恢复任务已经完成。

### 6. 验证

至少进行两类验证。

**结构完整性：**

- 数据库完整性检查；
- schema 是否可读取；
- 关键表、索引或约束是否合理。

**任务语义：**

- 用户要求的数据是否真正存在；
- 关键行、事务或对象是否恢复；
- 数量、字段和值是否符合任务预期。

结构检查通过不代表任务要求的数据一定恢复正确。

### 7. 报告结果和不确定性

结束前明确：

- 使用了哪些输入证据；
- 最终恢复输出在哪里；
- 进行了哪些验证；
- 是否存在未恢复、无法判断或可能不可靠的数据。

## 不适用场景

普通 SQL 编写、正常 schema migration、查询优化或常规数据库开发，不应仅因为使用了数据库就加载本 Skill。

只有任务涉及数据恢复、损坏、异常事务状态、日志恢复或可能破坏原始证据的调查时才使用。
